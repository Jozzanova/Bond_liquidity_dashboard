How the profile is computed

(click to expand; the full method is on the Methods & sources tab)

Holding in market m = portfolio size × allocation share, converted to local currency at the ECB reference rate (). With the maturity option off (the default) the holding is one pool sold against the market's turnover across all maturities, which is the same as holding the market in proportion to its turnover. With the option on, the holding is spread over the five maturity buckets with the weights entered (default: the market's outstanding stock by remaining maturity, see the outstanding stock table on the Methods & sources tab), buckets beyond the maturity limit are removed (a bucket the limit cuts through keeps a proportional share), the weights are rescaled and the buckets pooled into the market's liquidity groups. Each group is sold at a constant pace equal to the participation rate times the group's average daily turnover in the chosen segment (after the haircut), all groups in parallel. For US Treasuries, the on-the-run share of the holding set in the side panel sells against on-the-run volume and the rest against off-the-run volume, as two parallel parts of each group; at 0 % the whole holding sells against off-the-run volume only. A market switched off in the side panel is left out and the allocation is rescaled over the rest. Each market tab can apply its own selling assumptions to that market alone (its holding stays linked to this tab); nothing here changes when it does. The curve is the sum over groups of min(holding, pace × days). "Days to sell" is where that sum reaches the holding; the combined profile sums markets in the base currency.

This is a capacity calculation, not a price-impact model: it says how many days of turnover a holding represents, at a participation rate you judge to be absorbable without moving the market. It assumes turnover stays at its window average while you sell, which stress episodes contradict; use the haircut for that. Dealer-to-customer volume is the relevant pool for an investor that trades with dealers; interdealer volume (shown as D2D) is the dealers' own recycling of risk and is included only in the "total" segment.

Updating the data

Every number on this page comes from files in rawData/, read by the Python pipeline and baked into the page at build time. Most sources are downloaded by the pipeline itself; four need a file fetched by hand because the issuer's site blocks scripts. This tab shows how fresh each dataset is and what to do to bring it forward.

Status by dataset

Status. up to date nothing newer is expected, or the source was checked after the expected date and had nothing new · refresh due an automatic source should have new data, run the pipeline with --refresh · new data likely a hand-fetched file is probably available · file needed no file at all.

Latest data point is the last period in the data; raw files updated is when the files in rawData/ were last written; next data expected is a rough publication date after which newer figures are probably available at the source.

Manual files

(click to expand: the files to download by hand)

These issuers serve their files behind a bot check, so the pipeline cannot fetch them. Download the file in a browser, drop it in the folder named, then run the update below. The pipeline always uses the newest file of each kind.

Running an update

(click to expand: the four steps)
  1. Put any new hand-downloaded files in their folders (list above).
  2. In the project folder run python -X utf8 pipeline/run_all.py --refresh. This downloads every automatic source (TRACE months, JSDA workbooks, Finanzagentur page, Bond Connect reports, ECB rates, the four outstanding-stock lists) and parses everything in rawData/ into data/liquidity.json.
  3. Run python -X utf8 build.py to rebuild the page and the Excel downloads.
  4. Publish with npx wrangler deploy and check the dates on this tab.

Why there is no update button here. This page is a static file on Cloudflare; the pipeline needs Python with pandas and openpyxl and the hand-downloaded files on disk, so there is nothing on the server that could run it or receive an uploaded file. Running updates from the page would need a small runner (for example a GitHub Actions job that the page triggers through a Worker endpoint, with uploads committed to the repository the same way). That is a separate piece of infrastructure and is not set up. The one exception is exchange rates: the worker that serves the page fetches the ECB reference rates when the page is opened, so the profile is always converted at the latest ECB rates even when the rest of the data is older.

Methods, sources and assumptions

How the liquidity profile is calculated, what each source measures and where the figures stop being data and start being assumptions. The datasets behind every chart can be downloaded at the bottom of this tab; the freshness of each one is on the Update data tab.

How the profile is computed

(click to expand)

Turnover segments

The profile sells into one of two pools per market. Dealer-to-customer is the turnover an investor trading with dealers competes for; total adds the interdealer leg and is an upper bound. The table shows what each source lets us count as each segment.

Sources and counting conventions

Each source counts turnover its own way (par or market value, one side or both, which reporters), so the dealer-to-dealer and total columns are not comparable across markets. Only the dealer-to-customer pool is used in the default profile.

Outstanding stock by remaining maturity

The market-weighted maturity profile offered as the default holding distribution when the maturity option on the Liquidity profile tab is on: nominal amount outstanding of each market's nominal coupon government bonds in the five buckets, by remaining maturity on the as-of date.

What is not in the data

  • No source reports turnover by both counterparty type and maturity except FINRA TRACE and the DMO maturity-band file. For Bunds and JGBs the counterparty mix of the latest window is applied uniformly to every maturity class.
  • Bunds and JGBs are classified by original maturity, so a 10-year Bund with three years left sits in the 5-10y group. The common buckets are on remaining maturity; the mapping is therefore approximate for those two markets.
  • France has no published turnover by maturity or counterparty: the OAT level is the Bund level times a scale factor. China's maturity profile is taken from ADB AsianBondsOnline shares (no sub-1-year bucket, 5-10y split by assumption) unless a ChinaBond per-issue export is supplied; China has no observable interdealer split, and the whole-market CGB figure is CCDC settlement data, all counterparties.
  • Turnover is measured differently across sources: par value (TRACE, JSDA), market value (DMO) or nominal gross (Finanzagentur). Reporting populations also differ (all FINRA members; the DMO's gilt-edged market makers; a subset of Bund auction-group banks; all JSDA members; Bond Connect only).
  • Trading-day calendars are maintained by hand for the US (SIFMA), UK, Japan and China; the euro area uses a flat 255 days.
  • Averages are over the latest window of each source (12 months for TRACE, JSDA and Bond Connect; four quarters for the DMO; one calendar year for the Finanzagentur), so the windows do not coincide exactly.
  • Headline turnover figures quoted elsewhere are usually larger than the figures here because they count everything the source reports. The JGB tab shows the full reconciliation for the JSDA number: headline, less T-bills, less auction allotments, less the second leg of member-to-member trades, gives the dashboard total; the US tab's figures table does the same for TRACE venues and on-the-run issues.
  • The profile is a capacity calculation at a constant participation rate. It is not a price-impact model, and it assumes turnover stays at its window average while the holding is sold; the haircut is the only stress device.
